Big picture

Click any node for detail. Skills run on the laptop in Claude Code, drive the cloud website. Cloud Scheduler ticks every 30 min and picks the next channel from rotation. Render-worker-v2 is the muscle — calls TTS / image / ASR services, ffmpegs the mp4, uploads to YouTube. The laptop agent does cross-engagement (Playwright likes/subs) on uploads via 49 burner profiles.

Authoring flow — skill → narration → render → upload

1. User invokes /make-history-short in Claude Code
2. Skill drafts narration (Claude API or Azure OpenAI)
3. Skill PUTs NicheVideo payload via:
       python -m pipeline.state_client put historyrecapped narrations <slug>
   → HTTPS POST to ytfactory-web /api/state/historyrecapped/narrations/<slug>
   → state_routes.py validates against pipeline/niche_schema.py:NicheVideo
   → if valid, writes to gs://ytfactory-prod-v2-state/<chan>/<kind>/<slug>.json
4. Skill kicks render via:
       python -m pipeline.skill_dispatch render --channel ... --script ...
   → HTTPS POST to ytfactory-web /api/jobs/from_script
   → web spawns ytfactory-render-worker-v2 Cloud Run JOB
5. render-worker reads narration from GCS, calls
       tts-chatterbox / -indicf5  (audio)
       image-flux2-klein           (per-beat images)
       faster-whisper (in-process) (caption alignment)
   ffmpeg-composes the mp4 to gs://ytfactory-prod-v2-artifacts/
6. render-worker invokes pipeline.upload (YouTube Data API)
       /secrets/youtube-token-<channel>/value mounted at /secrets/...
7. Upload record written to gs://ytfactory-prod-v2-state/<chan>/uploads/<slug>.json

Cron flow — scheduler tick (every 30 min)

1. Cloud Scheduler ytfactory-tick fires
2. POST /api/scheduler/tick on ytfactory-web (OIDC token, IAM-validated)
3. control/scheduler.py:tick():
   - cap-check: skip if MAX_HEAVY_IN_FLIGHT (=2) tasks already queued
   - read scheduler_state/main from Firestore (last_channel)
   - round-robin pick next channel (channel_rotation() from channels.yaml)
   - find oldest narration in gs://...state/<chan>/narrations/
     that has no matching uploads/<slug>.json
   - enqueue RENDER_SHORT task in Firestore tasks/
4. render-worker-v2 picks it up + runs the same flow as steps 5-7 above

Cross-engagement flow — laptop agent

1. After upload, web enqueues a burner_engage lease task
2. Laptop com.ytfactory.laptop-agent.plist long-polls /agent/lease
3. Picks up the task, runs pipeline.burner_engage:
   - Iterates over the 49 burners in pipeline/burners.yaml
   - For each, spins up Chrome with that burner's profile (laptop-local)
   - Playwright likes + subscribes the new upload
4. ACK back via /agent/ack/<task_id>

Architectural wins so far

Single source of truth (pipeline/channels.yaml + burners.yaml)

Channel data is now configuration, not code. Adding a channel = YAML edit. control/scheduler.py CHANNEL_ROTATION, pipeline/niches.py NICHE_CHANNEL, pipeline/niche_schema.py NICHE_REGISTRY all derive from this one place. No aliases (one canonical slug per channel).

Universal NicheVideo schema

Every niche emits the same JSON shape — title + hook + narration + ordered beats + closer + render config + validation gates. State API rejects malformed payloads at the boundary (HTTP 422 + structured Pydantic errors). 22 niches registered, 5 wildly different niches round-trip in tests proving universality.

Skill-to-cloud I/O contract

28 skills updated. Producer skills (22) carry the NicheVideo + state_client banner; cross-cutting / meta skills (5) carry a "not a niche producer" marker. Schema enforced at PUT — skills self-correct on 422 errors without per-skill validators.

Web absorbs control (Phase 4)

All 16 control routers mounted into web/server.py at end-of-file (so web's own paths win on collision). Single canonical service. cloud/web-server is the only deploy target. cloud/control-plane retired with exit 1 guard.
